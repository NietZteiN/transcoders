#### Addendum, same day — the dense corpus is now *in* the browser (not just summarised)

The earlier pass added the **verdicts**; the browser still shipped only the banked corpus, so the
4,653 readings N5 actually produced were nowhere a reader could see them. Fixed:

- **New producer [`../../nla/src/anchor_dense_reads.py`](../../nla/src/anchor_dense_reads.py)** — the
  dense corpus stores token `position` and `u_rel` but no character offsets (the capture runner never
  needed them), and the browser highlights exact tokens. Rather than let the page re-derive geometry —
  a second copy of the alignment arithmetic is precisely what `capture_core.align_reply` exists to
  prevent — this recomputes it once through the shared function and **gates on the recorded token
  strings: 4,421/4,421 verified, 0 mismatched.** Reads whose span cannot be verified are never emitted.
- **Merged by token position**, banked rows winning ties: they are byte-identical (the 232 reused reads
  were verified to match exactly) and carry richer metadata (`cls`, `drm_ar`). Dense rows only ever add
  positions. **5,090 → 9,511 readings**; the 182 dense cases go from ~13 to a **median 37** readings
  (range 22–72). Each dense read is badged with its role (sweep 2,855 · strip 1,538 · burst 28), and a
  **Coverage → deep** filter isolates them.
- **Two evidence panels** built from `n7_results.json` and `ht14.json` — the judge's matched/distant/
  shuffled score bars, and the own-answer-vs-decoy bars. Every number is derived at build time; the one
  figure I had hand-typed (the second judge's modal-answer share) is now computed from
  `verdicts_phi.jsonl`. These show *what the instruments did*, so the verdicts read as evidence rather
  than assertion.
- Page 6.14 → **10.60 MB** (cap 16). Regression re-run on the enlarged payload: **7,249 marks, 0
  readings lost, 0 text corruption**; shipped JS passes `node --check`.

**Two bugs of my own, both caught by checking rather than assuming:**
1. Dense anchors initially carried only `{rs, re, in_reply}`, so `readHTML` silently skipped the
   token-context strip — the card's central promise — for every dense read. Anchors now match the
   banked schema exactly (`s/e/rs/re/tok/word/before/after`).
2. `_word_at` walked outward from the raw span start, so token `" by"` (leading space) walked left into
   the previous word and reported **"piece of `step by`"**. Fixed to trim to the token's own word
   characters first, and tightened further: a parent is claimed **only when the token is a strict
   sub-word**, otherwise `.push` rendered as "piece of `push`" — true but useless, and it buried the
   ~660 badges that carry real information (`tNSec` → `_lastNSecs`). Unit-tested on four shapes.

**Known inconsistency, deliberately not "fixed":** banked anchors were produced by the original capture
code and use its looser parent-word rule, so a banked and a dense read of similar tokens can badge
differently. Rewriting the banked anchors would mean editing a recorded corpus to match a display
convention, which is the wrong trade. Noted here instead.

#### Second addendum — scoping the stats, and a test that enforces it

Asked whether the stats and tests now cover every run. Checking rather than assuming turned up one
real inconsistency and settled one design question.

- **Headline counts were already correct** and are all derived, not typed: `stats.reads` = **9,511**
  (banked 5,090 + dense 4,421), 380 cases, 25 readings/run. The dense merge sits above the stats block
  in the builder, so the counts picked it up.
- **But the faithfulness section was silently mis-scoped.** It printed "Each of the 5,090 readings…"
  directly under a header saying 9,511 — two true numbers that read as a contradiction. It now states
  its scope explicitly and says why.
- **The dense readings are deliberately NOT pooled into that analysis**, and this is the substantive
  call, not an omission:
  - `byClass` is **structurally impossible** for them — dense reads were taken at reasoning positions
    and carry no identifier class (`cls` absent, verified).
  - `byVerdict` is the **retracted** chart; recomputing it on pooled data would be worse than leaving
    it.
  - `byTier` / `byDepth` / `hist` / `overall` *could* pool arithmetically, but the dense pass
    over-samples the 0.70–0.90 trough and covers a balanced 91-right/91-wrong subset, so a combined
    mean would reflect **which readings were taken** rather than what they found. That is precisely
    the composition trap behind the retracted HT12 result and the N5 drift-gate lesson
    ([`2026-08-06_n5-dense-results.md`](2026-08-06_n5-dense-results.md), observation 1). Repeating it
    one section above the retraction would have been indefensible.
- **New test [`../../nla/tests/artifact_stats_test.mjs`](../../nla/tests/artifact_stats_test.mjs)** —
  asserts every printed number is recomputable from the shipped payload, and that a section covering a
  subset states an n **equal to that subset and strictly below the page total**, so the scope note
  cannot silently become false. Also checks per-reading integrity across both corpora. Result:
  380/9,511 · banked 5,090 + dense 4,421 · faithfulness scoped at 5,090 · **0 empty readings, 0 missing
  scores, 0 broken anchors, 0 duplicate positions**. Suite is now three files, all passing.

**Analyses, for completeness:** N6 ran on **both** corpora, reported separately and never pooled (that
separation is the finding). N7 and N8 are dense-only *by design* — HT13 and HT14 were pre-registered
against the matched corpus, so running them on the banked set would be a different, unregistered test.

#### Third addendum — six figures, and the judge run drawn properly

The verdicts were prose with three bars. The judge run is the largest thing collected (5,653 blinded
comparisons) and had almost no visual representation. Rebuilt as six inline-SVG figures.

- **New producer [`../../src/analysis/n7_chartdata.py`](../../src/analysis/n7_chartdata.py)** — the
  series live in version control beside the analyses that produced them, not inside the renderer. The
  page builder draws; it never derives a statistic. Series: judge score histogram per condition · ROC
  for judge **and** the AR baseline · Llama×Phi 4×4 agreement · alignment across trace position
  (cluster-bootstrapped over cases) · HT12's decomposition arms · HT14's excess-over-null per decile.
- **New renderer [`../../nla/tools/charts.py`](../../nla/tools/charts.py)** — hand-built SVG (strict
  CSP, no external requests), themed through CSS custom properties.
- **Colour was computed, not chosen.** Every hex ran through the data-viz validator against **both**
  page surfaces before being written down. Rejected *by the validator*: the page's own semantic
  green/red (`--ok`/`--bad`) — failed the chroma floor and sat at CVD ΔE **6.8**, the classic red/green
  trap; and blue+violet — collapsed in dark mode (CVD ΔE **1.9**, normal-vision **9.8**). Shipped:
  correct/wrong = blue+orange, judge/baseline = blue+red, scores 0–3 = a 4-step ordinal blue ramp, all
  passing every gate in both modes. `correct` and `wrong` keep the same two hues in every figure.
- **Rendering them and looking caught four bugs that no structural check would have.** I rendered each
  figure to PNG with `rsvg-convert` and inspected it:
  1. forest plot — value labels collided with the top row's CI whisker (no right column reserved);
  2. ROC — **no axis tick labels at all**, and half the card was dead space (fixed with a tailored
     viewBox so CSS scales the square up);
  3. heatmap — the summary line overran the tailored viewBox and was clipped (moved into HTML);
  4. **the real one: white-on-dark labels were not applying.** A CSS class rule beats an SVG `fill`
     presentation attribute, so `.fig .vl{fill:var(--ink-2)}` silently overrode `fill="#fff"` — dark
     text on the darkest cells and segments. Fixed with explicit classes.
  Then a **fifth, only visible in dark mode**: `.onlight{fill:var(--ink)}` flips to near-white when the
  theme flips, but the s0/s1 bar segments are pale blue in *both* themes, so those labels washed out.
  The bar labels now use a pinned dark ink; the heatmap keeps the theme-following one, because its pale
  cells genuinely are surface-derived. Two classes that look interchangeable and are not.
- Page **10.63 MB** (cap 16). All three regression tests still pass; six figures parse; JS clean.

**Observation worth keeping:** the palette validator and the SVG structure check both passed on the
*first* render, which had misplaced labels, no tick marks, a clipped line and unreadable numbers on
four cells. Neither tool looks at layout. Rendering to an image and actually looking is not optional
polish — it is the only step that catches this class of defect.
