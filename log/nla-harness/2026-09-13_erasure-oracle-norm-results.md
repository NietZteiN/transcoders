- **What worked / hypothesis verdict:**
  - **H-E14 ✓ `ORACLE-FREE` at all three sites — the caveat I raised this afternoon costs the claim nothing.** The published memo's claim 2 is repaired rather than narrowed: a mean-difference vector that borrows **nothing** from `h0` — direction *and* magnitude estimated from the other items' spans — still scores +34.21 at 4B L7 against the trained edit's +32.06, and is still directional at +12.13 [+8.36, +15.79]. The "training-free baseline any such method must clear" is now genuinely **deployable**, which is what it was always claimed to be and was not.
  - **H-E14b: `DEPLOYABLE-DIRECTIONAL` at both 4B sites, `DEPLOYABLE-NOISE` at 12B L32 — ✓ as predicted.** Removing the oracle does not rescue the 12B site; it leaves it exactly as null (−0.38 [−1.58, +0.85] vs the oracle version's −0.46 [−1.71, +0.80]). So H-E7c's refutation was never an artifact of the oracle either, and the two host-level answers are now each backed by two independent controls.
  - **My `ORACLE-SCALED` prediction at 4B L13 is ✗ REFUTED, and the reason was in the same day's data.** The estimated magnitude is *better* than the true one (−1.16). At L13 the α ladder turns over hard (`erase_2.0` collapses to +11.02 from +32.61) and the true per-span norms have CV 0.53, so the oracle hands some spans a destructively large step; the leave-one-out mean is a **shrunken** estimator that pulls them back toward safety. **At a site where overshooting is destructive, the true magnitude is variance, not information.** I reasoned "magnitude matters more here, so the oracle is worth more" when the correct reading was "magnitude *errors* matter more, and the estimate is the safer of the two". That is four predictions missed today out of six, and this one was avoidable from measurements already in hand.
  - **A gate finding with programme-wide reach: the 0.05-nat identity tolerance is not portable across GPU architectures at 12B.** The same code, same vectors, same seed refused on h100 and passed at exactly 0.0 on h200. The decisive detail is **`self` = 1.0017**: `self` writes the state the model already has and is scored against an unsteered baseline *computed inside the same run*, so this cannot be stale bytes or a wrong file — on that hardware the hook path itself perturbs the bf16 numerics of a 12B forward enough to move a ~700-token summed logp by a nat. The 4B sites reproduce on either architecture, so the effect is scale-dependent (L32 activations have norm ~56 585). **CLAUDE.md §4 already required logging the GPU id; this is the first result showing it is a correctness requirement, not bookkeeping** — every 12B banked row in this programme is only reproducible on h200 nvl, and the re-run script now hard-refuses any other architecture rather than producing quietly contaminated numbers. Related in kind to defect #14 (bf16 write chaos) — same root cause, a tolerance that assumes numerical reproducibility it does not have — and this is the **fourth specification-class fault found today**.
