### Target Date: 2026-09-14 (AMENDMENT to the H-R1 pre-registration — case packs are rebuilt per obfuscated variant, not held fixed)

- **Why this exists.** [`2026-09-14_ase-replication-prereg.md`](2026-09-14_ase-replication-prereg.md) specified the renamed condition as "the RENAMED condition swaps only the code; the case pack (and so the ground truth) is untouched". **That is not their protocol.** `obfuscation/main.py:428` calls `build_case_pack(java_code=code, ...)` where `code` is the **obfuscated variant**, and the oracle labels are then taken from `case_pack` after executing that variant (`utity.run_java_program_with_result(code, ...)`, with a hard failure if it does not compile). Case packs are therefore **rebuilt per variant**. Recorded as an amendment rather than an edit, per CLAUDE.md §6; **no H-R1b data exists yet**, so the design may still be fixed — only the description changes, and no threshold moves.
- **What changes in the design:**
  - The renamed condition is produced by running the pack builder **on the renamed Java**, yielding `packs_renamed_*.jsonl` whose `java_path` points at the renamed file. `ase_tf_run.py` then needs no new flag — it already serves code from each pack record — so the `--code-root` override added for the old design is **removed** to prevent it being used by accident and silently reproducing the wrong protocol.
  - Labels are re-derived by executing the renamed program. Renaming is semantics-preserving, so labels *should* match the original condition; any snippet where they do not is a **renamer bug**, not a finding, and is quarantined.
- **Why this strengthens the hypothesis rather than weakening it.** Every case expression is of the form `s.hasCloseElements(new ArrayList<>(Arrays.asList(11.0, 2.0, ...)), 0.3)`. Because packs are rebuilt on the renamed source, the renamed condition asks the model to evaluate `s.superParent(new ArrayList<>(...), 0.3)` — the method name is gone **from the question text**, 8–16 times per prompt, not merely from the code body. That is precisely the mechanism the prereg nominated for their −36.3-point drop (HumanEval-X, 76.49 → 40.20, *below* the 50 % chance floor set by the negation-paired cases), and it is a manipulation my Python/JS output-prediction setup applies far more weakly.
- **A new gate this forces, frozen now:** **pack correspondence.** For each snippet the renamed pack must have the **same case count** as the original pack and the same per-case `expected_bool` sequence, since seeds are extracted from the in-program harness and structure-preserving renaming should not change them. **`PACKS-PAIRED`** if ≥ 95 % of snippets correspond → the Pass@1 comparison is snippet-paired *and* case-paired. **`PACKS-UNPAIRED`** otherwise → the comparison is snippet-level only, the case-level pairing claim is dropped, and the mismatching snippets are reported. This is a limitation of the original design that only became visible on reading their code, and it applies to **their** published comparison too: nothing in their pipeline guarantees the obfuscated variant yields the same case set as the original.
- **Unchanged:** every H-R1a/H-R1b threshold, the model (`llama8b`), the decoding regime (T = 0.7, top_p = 1.0, sampled, 3 runs), Pass@k as a case-weighted proportion, and the standing caveat that the renamer is **mine** because their generator is excluded from the artifact.
